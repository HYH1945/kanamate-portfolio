01 문제 정의

일반 챗봇은 “다음 주 화요일 3시 어떠세요?”라는 그럴듯한 문장을 만든다. 그런데 그 문장은 —

  • 내 기존 일정과 충돌하는지 확인한 적이 없고,
  • 팀원이 실제로 그 시간에 가능한지 근거가 없고,
  • 앱이 읽어서 저장할 수 있는 데이터도 아니다.

그래서 “모델이 무슨 말을 했는가”가 아니라 “어떤 tool을 어떤 인자로 호출했고 어떤 row가 남았는가”를 1급 관심사로 두는 일정관리 에이전트를 설계했다.

설계 원칙은 하나다. Supervisor는 업무 tool을 직접 호출하지 않는다. delegate tool만 호출하고 각 sub-agent의 내부 trace를 근거로 최종 답을 만든다 — 책임이 섞이면 누가 무엇을 잘못 판단했는지 추적할 수 없기 때문이다.

04 기술적 의사결정

병렬 tool 호출을 차단해 실행 순서를 보장

LangChain agent는 기본적으로 tool을 병렬 호출한다. 하지만 search_previous_conversations → extract_schedules_from_history → decide_final_slot은 앞 결과가 뒤의 입력이 되는 파이프라인이다. 미들웨어로 순서를 강제해 trace가 매번 같은 모양으로 재현되게 했다.

class DisableParallelToolCalls(AgentMiddleware):
    def wrap_model_call(self, request, handler):
        request.model_settings["parallel_tool_calls"] = False
        return handler(request)

원본 payload와 정규화 row의 이중 저장

모델이 만든 tool arguments 전체를 payload_json에 원본 그대로 남기고, 동시에 kind에 따라 schedules / todos / reminders로 정규화한다. 정규화 row만 남기면 모델이 무엇을 어떻게 잘못 구조화했는지 사후 분석이 불가능하다.

검색 tool을 대상별로 분리

자유 서술형 메모는 embedding 검색, 구조화 저장된 일정은 row 검색으로 나눴다. 하나로 합치지 않은 이유는 질문의 성격에 따라 검색 대상을 고르는 것 자체가 agentic 판단이고, 그 판단이 trace에 남아야 하기 때문이다.

역할 경계를 프롬프트가 아니라 도구 구성으로 강제

Kana에게는 개인 일정 tool을 아예 주지 않아, 내 일정 충돌 여부를 임의로 판단할 수 없게 만들었다. 개인 일정 판단은 Nana의 trace에서만 나온다.

05 검증

“답변이 그럴듯한가”로 동작을 판정하지 않기 위해 두 겹의 검증을 넣었다.

  • Trace assertion — tool 호출 순서와 저장 row count를 assert로 고정.
  • LLM-as-a-judge — supervisor trace와 delegate payload JSON을 judge 모델에 넘겨 6개 체크리스트(위임 순서, 역할 침범 여부, 최종 답변의 근거 반영 등)로 판정. 첫 줄이 PASS가 아니면 실행이 실패한다.

재현성은 uv.lock과 langgraph-prebuilt==1.0.8 핀으로 고정했다. LangChain 1.x의 create_agent import가 이 전이 의존성 버전에 민감해 실제로 환경이 깨진 적이 있어, lockfile과 별개로 직접 핀을 박았다.

결과

골든 케이스(“팀원 A/B/C와 다음 주 회의 시간을 잡아줘”)에서 supervisor가 nana_agent → kana_agent 순서로 위임하고, 내 일정 충돌 확인과 팀원 가능 시간 후보를 모두 반영한 최종 시간과 선택 근거를 산출. judge 검증 PASS.
