03핵심 설계 · 고르는 건 Agent, 검증은 Python

Kana가 회의 시간을 정하는 다섯 단계

  1. Tool수집 · 나와 팀원의 바쁜 시간 모으기
  2. Agent후보 선택 · 바쁜 시간을 읽고 비는 시간 후보 고르기
  3. Tool검증 · 후보가 누군가의 일정과 겹치는지 확인
  4. Agent확정 · 후보 하나와 선택 이유 결정
  5. Tool기록 · 결정 내용을 payload로 저장

Python이 시간을 직접 계산하면 왜 그 시간인지가 기록에 안 남고, LLM에만 맡기면 겹침을 확인할 방법이 없음. 그래서 선택은 agent, 검증과 기록은 tool이 맡도록 나누고 같은 규칙을 tool 설명과 prompt 양쪽에 명시

04설계 결정

역할 경계는 prompt보다 tool 구성으로 W6

Supervisor는 하위 agent 2개만 호출 가능, Kana에는 저장 tool 자체가 없음. 지시문 대신 쓸 수 있는 tool로 역할을 제한

원본과 정규화 데이터를 함께 저장 W3

LLM이 만든 구조화 결과 원본을 그대로 남기고, 종류별로 일정·할 일·알림 테이블에 나눠 저장. LLM이 무엇을 잘못 구조화했는지 나중에 추적 가능

여러 출처의 일정을 한 결과로 병합 W5

내 일정(SQLite)과 팀원 일정(MCP)을 하나로 합칠 때 날짜 필터를 양쪽에 똑같이 적용하고, 외부 조회에서는 나를 제외해 중복 제거. 외부 서버가 실패해도 내 일정은 유지하고 실패 여부만 함께 반환

검색 임계값은 실측으로 W4

관련 질문은 distance 1.08 이하, 무관한 질문은 1.34 이상으로 측정돼 그 사이인 1.2를 기준으로 무관한 결과를 필터링

05문제 해결

취향을 말해도 저장이 안 되고, 대화 검색과 저장 기록 검색이 뒤섞임 W4

해결tool 이름 나열 대신 어떤 질문에 어떤 tool을 쓰는지 예시 중심으로 prompt를 다시 작성

철수와의 대화 검색 요청이 Nana로 위임됨 W6

해결다른 사람이 언급된 대화·일정 요청은 Kana로 보내는 기준을 Supervisor prompt에 추가

다음 주 화요일 같은 상대 날짜를 잘못 해석 W6

해결오늘 날짜를 Kana prompt 맨 앞에 넣어 기준점 제공

공통 시간이 없으면 기록 없이 대화가 끝남 W6

해결후보가 없어도 결정 tool을 호출해 보류 상태와 이유를 남기도록 변경

공통 교훈 · tool 설명과 prompt에 적히지 않은 규칙은 agent가 지키지 않음. W4 라우팅 버그와 W6 계약 설계 모두 같은 원인이었고, 이후 새 tool을 붙일 때마다 tool 설명, prompt, 실제 코드가 같은 규칙을 말하는지부터 점검

또한 W6의 세 건은 모두 정상 흐름이 아닌 예외 상황에서 발생. 빈 결과, 필터 없는 기본값, 외부 호출 실패를 정상 케이스와 별도로 확인하는 습관이 생김

06결과와 한계

결과
그룹 일정 요청에 검증된 후보 중 최종 시간과 선택 이유를 기록, 후보가 없으면 보류와 사유를 기록
한계
최종 확정 tool이 agent가 넘긴 시간을 검증된 후보와 다시 대조하지 않음. 과거 실행 기록 중 겹치는 시간이 확정된 사례 1건 확인
Supervisor가 확정 후 불필요하게 Nana에 저장을 다시 요청하고, Nana의 거절 문구가 최종 답변에 섞이는 경우가 있음
팀원 데이터는 실습용 고정 데이터, 검증은 Trace 육안 확인 위주
다음 단계
확정 시간을 검증된 후보 목록과 대조, 확정 이후 위임 종료 규칙을 Supervisor prompt에 추가, tool 호출 순서 회귀 테스트
